| 2026-07-12 | **D-b — o áudio final mantém a duração exata do vídeo.** Hoje `buildDubTrack` estende o buffer para preservar a cauda da última fala (`mixer.dart:16-24`) e `amix=inputs=2:duration=first` (`mixer.dart:61,78`) a descarta — as duas funções do mesmo arquivo se contradizem, e a fala final é truncada sem aviso. Decisão: o agendamento passa a tratar o fim do vídeo como deadline do último run (com teto de velocidade dedicado, acima do `maxTotalSpeed`/`atempoMax` normais); o que ainda assim sobrar é cortado, **medido e reportado** (`truncatedTailMs`). A regra #4 da spec desktop ("nunca trunque fala dublada") ganha exceção explícita com teto (`tailTruncationCapMs`). Alternativas descartadas: `duration=longest` (áudio mais longo que o vídeo) e freeze-frame com `tpad` (exigiria re-encodar o vídeo, quebrando `-c:v copy`). |
| 2026-07-12 | **D-c — modelos Android são espelhados como `.tar.gz` em Release próprio**, com SHA-256 fixado. SHA-256 passa a ser obrigatório nas entradas novas; as 64 entradas desktop legadas seguem sem hash. |

| 2026-07-13 | **Achado — a sincronia do pipeline não é 100% reprodutível, e o `tool/integration_test.dart` escondia isso.** O teste regerava a fixture com o Piper a cada execução; o Piper é um VITS com `noise_scale_w=0.8`, ou seja, síntese **estocástica** → áudio de entrada diferente a cada run → timestamps e segmentação diferentes (medido: 4–6 unidades para o mesmo texto; sincronia 83%–100%). Corrigido: a fixture agora é gerada uma vez e reusada (apagar o jobDir força uma nova). **Porém**, mesmo com fixture de SHA-256 idêntico, a segmentação ainda oscila 5↔6 unidades: whisper-cli e o spleeter são individualmente determinísticos (transcript/vocals com hash idêntico em 3 execuções), mas a inferência nativa multi-thread sob carga introduz jitter sub-ms nos timestamps que ocasionalmente cruza o limiar de merge (`mergeMaxPause = 600ms`), criando/removendo uma unidade. É uma fragilidade pré-existente (não do refactor do DubbingRuntime) e relevante para o baseline de ±300ms da fase D1: o baseline precisa ser uma faixa/mediana de N execuções, não um número único. |
| 2026-07-12 | **Bug corrigido — o fallback de re-encode do mux nunca funcionou.** `muxer.dart` pedia `-c:v libx264`, mas o ffmpeg distribuído em `tools/win/` é build LGPL com `--disable-libx264` (conferido no `-buildconf`): o encoder **não existe no binário**. | 2026-07-14 | **Achado — `adb push`/`adb shell mkdir` para dentro de `Android/data/<pkg>/files` cria arquivos invisíveis ao próprio app.** Descoberto ao rodar o AT-2 no device: qualquer diretório/arquivo criado via shell (uid `shell`) dentro da pasta externa de um app dá `Permission denied` quando o **próprio app** (uid próprio) tenta `existsSync`/`createSync` no mesmo caminho — mesmo sendo a pasta do próprio app. Só sobrevive o que o processo do app cria diretamente. Contorno usado no spike: enviar os assets para `/data/local/tmp` (sem isolamento por app) e o app copiar para sua própria pasta no primeiro start. **Não afeta produção** — lá o `ModelManager` sempre baixa/escreve pelo processo do app, nunca via adb. | 2026-07-14 | **Achado de ambiente — build Gradle/Flutter no Windows pode esgotar memória VIRTUAL (commit charge), não RAM física.** Ao compilar o app de benchmark do AT-2, `flutter build apk` crashava o daemon Gradle/JVM com OOM repetidamente mesmo com RAM física livre — `Get-CimInstance Win32_OperatingSystem` mostrava `FreeVirtualMemory` baixo (pagefiles fixos, não auto-gerenciados nesta máquina: `C:\pagefile.sys`=4073 MB, `E:\pagefile.sys`=8192 MB). É um teto de commit charge do SO, distinto de falta de RAM. **Mitigação que funcionou** (`android/gradle.properties`): `org.gradle.jvmargs=-Xmx512m -XX:+UseSerialGC -Xss512k` (G1GC reserva muito mais espaço virtual de saída que o Serial), `org.gradle.daemon=false`, `org.gradle.workers.max=1`, `kotlin.compiler.execution.strategy=in-process` (evita um segundo JVM só para o compilador Kotlin). **Armadilha decorrente:** se um build travado for cancelado, o processo Java filho pode sobreviver ao encerramento do processo pai (shell) e ficar segurando o lock `<GRADLE_USER_HOME>/caches/journal-1/journal-1.lock` — o próximo build falha em segundos com "Timeout waiting to lock journal cache", parecendo um novo erro quando é só um daemon zumbi. Sob essa pressão de memória, `tasklist`/`taskkill` (utilitários clássicos do Windows) também podem travar/dar timeout; `Stop-Process -Id <pid> -Force` do PowerShell (via API .NET) contorna. |
