| 2026-07-11 | Expansão de idiomas (3→23): `enum Lang` virou *enhanced enum* (Dart 3) com metadados (`code`, `label`, `iso639_2`, `isDubTarget`, `whisperCode`) em vez de switches exaustivos espalhados — com 23 valores, um switch por local de uso seria muito mais frágil que um construtor obrigatório por valor. |

| 2026-07-11 | **Achado empírico**: o I/O do translateLocally por arquivo (`-i`/`-o`) usa o encoding local do sistema (cp1252 no Windows) — mas por **stdin/stdout** ele é UTF-8 puro (testado com bg-en-tiny e caracteres cirílicos). | 2026-07-11 | Sérvio: o modelo `hbs-eng-tiny` só traduz corretamente em script latino — cirílico produz saída sem sentido (testado: "Мачка спава на каучу." → "I'm on it."). Como o alfabeto cirílico sérvio tem correspondência 1:1 com o latino (reforma de Vuk Karadžić), o texto de origem sérvio é transliterado cirílico→latino antes da tradução (`_serbianCyrillicToLatin` em `translatelocally_translator.dart`), sem perdas. |
| 2026-07-11 | Búlgaro (`bg`) tem tradução `en↔bg` mas **nenhuma voz piper mirrorada** no release `tts-models` do sherpa-onnx (confirmado por HEAD 404 nas duas variantes de nome + ausência na documentação oficial) — por isso ficou como língua só-origem (`isDubTarget: false`), diferente do plano inicial que previa 5 alvos novos (ficaram 4: de/fr/pl/cs). |
| 2026-07-11 | Vozes piper novas validadas via HEAD contra o release do sherpa-onnx (não a API do GitHub, que tem rate limit agressivo para requisições anônimas) — script `packages/dubbing_engine/tool/gen_voice_manifest.dart`. IDs de voz legados (`piper-pt-br`, `piper-en` etc.) são imutáveis: são nomes de diretório em disco e ficam persistidos em `settings.voiceModelId`. |
| 2026-07-11 | **Achado empírico** (durante spike de port Android, `omnitranslator-android`): os modelos de tradução `en-pt-base`/`pt-en-base` (tipo `base-memory`) estão instalados em `%LOCALAPPDATA%\translateLocally\{enpt,pten}\` e traduzem normalmente — **português funciona no desktop**. Porém eles **não aparecem** em `translateLocally -a` (registro de download atual; só no `-l`, modelos já instalados), ou seja, vieram de uma versão anterior do models.json público. **Risco não confirmado**: `scripts/download-models.ps1` documenta que os modelos de tradução são baixados sob demanda via `translateLocally -d <id>` — não foi testado (para não apagar o modelo em uso) se `-d en-pt-base` ainda funciona numa instalação nova, já que o par sumiu do `-a`. Se alguém fizer setup do zero e o `-d` falhar, dublagem para/de português ficará indisponível até achar outra fonte para esses dois arquivos de modelo. |
| 2026-07-11 | Android e Windows ficarão no **mesmo repositório e no mesmo app Flutter** (`app/windows` + futuro `app/android`). O protótipo `omnitranslator-android` é somente fonte de spikes; não será uma segunda implementação nem consumirá o engine por dependência Git. |
| 2026-07-11 | Android M1 foi reduzido a arquivo local en/pt/es, Whisper tiny/base ONNX, tradução local, uma voz Piper, voice-over com ducking e SRT. Separação, diarização/múltiplas vozes, YouTube e tempo real têm marcos posteriores para não misturar riscos independentes. |
| 2026-07-11 | O port não será apenas troca de factories: antes dele, `dubbing_engine` receberá `DubbingRuntime`, runners tipados, extração injetável, áudio de segmentos em disco, writer WAV sequencial e checkpoints. Motivo: o pipeline atual mantém áudios e uma faixa do tamanho total do vídeo em `Float32List`, inadequado para mobile. |
| 2026-07-11 | ~~Português é **gate de release Android**. Slimt fica aprovado apenas para modelos tiny; en↔pt `base-memory` deve passar a suíte AT-1 com configuração completa.~~ **SUPERADA em 2026-07-12** pela decisão D-a: o slimt não carrega `base-memory` em nenhuma configuração. Permanece válido que **português é gate de release** e que o único fallback é bergamot-translator via NDK (não NLLB, não um terceiro backend). |
| 2026-07-11 | Android usará **FFmpegKitNext oficial**, inicialmente tag 8.1.0 com commit registrado no spike, compilado do código-fonte em variante LGPL e sem `--enable-gpl`. Media3 não cobre `atempo`, `sidechaincompress`, `loudnorm` e toda a semântica atual do pipeline. |
| 2026-07-11 | Jobs Android longos usarão foreground service direto `mediaProcessing`, estado persistido e FlutterEngine headless; WorkManager não executará o pipeline. Entrada/saída usam SAF, espaço usa `StatFs`, `minSdk` é 28, release é arm64 e todas as `.so` devem passar compatibilidade de páginas 16 KB. |
| 2026-07-12 | **Achado externo — o slimt só suporta a arquitetura `tiny`.** O README do projeto diz textualmente *"Eventual support for `base` models are planned"*. A falha do SA1 §8.3 com `en-pt-base`/`pt-en-base` (`base-memory`) não era configuração errada de hiperparâmetros: é arquitetura **ausente** no slimt. Consequência: os passos 3–4 da §10.2 da spec Android ("inspecionar a arquitetura do base-memory", "executar slimt com todos os hiperparâmetros corretos") são um beco sem saída e foram removidos. |
| 2026-07-12 | **D-a — Android traduz com modelos `tiny`.** O desktop mantém `base-memory`. A divergência de qualidade é **aceita conscientemente** — e, medida, é irrelevante: os `metadata.json` da Mozilla publicam BLEU/COMET no FLORES, e nos pares de gate a perda do tiny é de **0,6 BLEU em en→pt (49,4 × 50,0)** e **0,1 em pt→en (47,8 × 47,9)**, com metade do tamanho (17 MB × 31,5 MB). O fallback bergamot-translator via NDK só é acionado se o tiny reprovar o AT-1, com time-box de 5 dias úteis. Detalhes em `docs/spikes-android/AT1.md`. |
| 2026-07-12 | **CORREÇÃO — o repo arquivado NÃO é fonte de download.** Eu havia registrado que `mozilla/firefox-translations-models`, por estar arquivado, daria URLs imutáveis. Errado: os modelos estão em **Git LFS** e os objetos **foram removidos do servidor** (batch API responde `410 Object does not exist`); `raw.githubusercontent` devolve só o ponteiro de 132 bytes. Arquivar preserva o histórico, não o armazenamento LFS. O que o repo ainda serve — e é útil — são os `metadata.json` (fora do LFS), com arquitetura, hash, tamanho e métricas de qualidade. |
| 2026-07-12 | **A fonte real dos modelos de tradução é o Remote Settings do Firefox.** Índice em `https://firefox.settings.services.mozilla.com/v1/buckets/main/collections/translations-models/records` (679 registros, com `fromLang`/`toLang`/`fileType`/`version` e um `attachment` com `location`, `size` e `hash` SHA-256); arquivos em `https://firefox-settings-attachments.cdn.mozilla.net/<location>`. **`version: "1.0"` = tier `tiny`** (17.140.899 bytes; `dec-cell: ssru`, `dec-depth: 2` — a arquitetura que o slimt implementa) e **`version: "2.x"` = `base-memory`** (31.561.787 bytes). Isso não é inferência por tamanho: o `hash` do `metadata.json` de `models/tiny/enpt` é idêntico ao `attachment.hash` do registro v1.0. Download verificado ponta a ponta (HTTP 200, 17.140.899 bytes, SHA-256 confere). ⚠ Os `location` são UUIDs **por versão** — fixar `location` **e** `hash` juntos no catálogo. |
| 2026-07-12 | **Fonte pública para o modelo de tradução do desktop — risco encerrado.** O `model.enpt.intgemm.alphas.bin` instalado em `%LOCALAPPDATA%\translateLocally\enpt\` foi hasheado e é **bit a bit idêntico** ao registro **v2.1** do Remote Settings (`07892fd2544ee79dcb643615d8f2debb9793fae16842e87c328e27a3dd26a770`); `lex` e `vocab` batem em tamanho. Encerra o risco registrado em 2026-07-11 ("se `translateLocally -d en-pt-base` falhar numa instalação limpa, pt fica indisponível"): existe fonte pinável, hasheável e redistribuível (MPL-2.0) para pt também no Windows. |
| 2026-07-12 | **D-b — o áudio final mantém a duração exata do vídeo.** Hoje `buildDubTrack` estende o buffer para preservar a cauda da última fala (`mixer.dart:16-24`) e `amix=inputs=2:duration=first` (`mixer.dart:61,78`) a descarta — as duas funções do mesmo arquivo se contradizem, e a fala final é truncada sem aviso. Decisão: o agendamento passa a tratar o fim do vídeo como deadline do último run (com teto de velocidade dedicado, acima do `maxTotalSpeed`/`atempoMax` normais); o que ainda assim sobrar é cortado, **medido e reportado** (`truncatedTailMs`). A regra #4 da spec desktop ("nunca trunque fala dublada") ganha exceção explícita com teto (`tailTruncationCapMs`). Alternativas descartadas: `duration=longest` (áudio mais longo que o vídeo) e freeze-frame com `tpad` (exigiria re-encodar o vídeo, quebrando `-c:v copy`). |
| 2026-07-12 | **D-c — modelos Android são espelhados como `.tar.gz` em Release próprio**, com SHA-256 fixado. Motivo: os assets do sherpa/Piper são `.tar.bz2` e o `BZip2Decoder` do `package:archive` é Dart puro e lento demais para o celular; no desktop a extração usa o `tar` do Windows, que não existe no Android. Efeito colateral: fecha a lacuna da §16.3 (hoje nenhuma das 64 entradas do manifest preenche `sha256`, então `_verifyAndWriteSha256` nunca compara nada — é trust-on-first-use). SHA-256 passa a ser obrigatório nas entradas novas; as 64 entradas desktop legadas seguem sem hash. |
| 2026-07-12 | **D-d — não haverá CI.** A §16.2 exigia gerar o inventário de `.so` "na CI", mas não existe CI no repositório. Em vez de criar uma, os gates viram scripts locais rodados à mão: `tool/verify.ps1` (analyze + testes, falha se regredir dos 199) e `tool/check_native_libs.dart` (inventário de `.so` por ABI/tamanho/hash/origem). |
| 2026-07-13 | **Caminho 3 escolhido — AT-1 PASSA com `dedupRepeatedTail` no backend.** Diante da reprovação abaixo, três caminhos foram avaliados: (1) corrigir o decodificador C++ do slimt, (2) fallback bergamot via NDK (5 dias; bônus: carregaria `base-memory` = paridade com o desktop), (3) **corte de eco em pós-processamento Dart** — escolhido por ser o único **já validado com dados**: aplicado sobre as 100 saídas reais do aparelho, elimina 17→0 frases degeneradas sem alterar nenhuma frase limpa (pt→en: ~75–85 → **~93–95 aceitáveis**; teto: 90). Implementado em `translation_postprocess.dart` com 4 regras que são propriedades do modo de falha (pontuação metralhada, 4-gram repetido, eco de sentença-prefixo, fragmento final repetitivo), e os casos reais do device como fixtures. **Nota de critério consciente:** o §10.4 é avaliado sobre a saída do backend completo (slimt + dedup) — é o que o usuário ouve; precedente: a transliteração sérvia já pós-processa a *entrada* no desktop. O `AndroidTranslator` (D3) DEVE aplicar `dedupRepeatedTail`. Bergamot permanece como fallback documentado se os vídeos reais do aceite mostrarem insuficiência. |
| 2026-07-13 | **AT-1 executado no moto g86: slimt cru reprovou — pt→en repete.** Com os modelos tiny v1.0 do Firefox (SHA-256 conferido), 100 frases/direção, sem `--shortlist`: **en→pt passa** (100/100 não vazias, ~96 boas, ~20 ms/frase, pico 114 MB, zero crash) mas **pt→en reprova** o critério "sem repetição degenerada" (~85% limpo por 4-gram estrito, ~75% na leitura humana). Padrão sempre "tradução correta + cauda repetida" (ex.: "I would like a cup of coffee. I would like a cup of coffee."). **Causa isolada:** decodificação **gulosa** do slimt (beam 1, sem normalização de comprimento nem penalidade de repetição, nada exposto na CLI) — não os modelos (traduzem certo) nem a arquitetura: **en→de tiny, mesma arquitetura/fonte/warnings, traduz limpo**. Achados de config: (a) o **shortlist (lex) degenera a saída** nas duas direções — o pacote Android usa só `model`+`vocab`, sem `lex` (−4,3 MB/par); (b) os warnings `Wemb_QuantMultA`/`special:model.yml` são **benignos** (en→de os mostra e funciona). §10.4 → slimt não aprovado. **Decisão pendente:** (1) corrigir o decodificador do slimt (temos o source; menor esforço, alta chance porque a tradução já sai certa antes do loop) ou (2) o fallback bergamot-translator via NDK (beam+normalização do Marian, carrega os mesmos modelos; item caro, time-box 5 dias). Relatório: `docs/spikes-android/AT1.md`. |
| 2026-07-12 | **AT-0 executado: 16 KB não é problema — PEND-2 encerrada.** As três `.so` arm64 do `sherpa_onnx_android_arm64` 1.13.4 (`libonnxruntime.so`, `libsherpa-onnx-c-api.so`, `libsherpa-onnx-cxx-api.so`) têm **todos** os segmentos `LOAD` com `align 0x4000` (16 KB), e o ORT embutido é **1.27.0**, não 1.17.1. A issue k2-fsa/sherpa-onnx#3291 está obsoleta em dois níveis: a versão do ORT subiu, e a lib de que ela reclama (`libonnxruntime4j_jni.so`) é o binding **Java** — o pacote Dart usa a C API e não empacota nenhuma lib `*4j*`. Consequência: o remédio caro (compilar sherpa-onnx + ONNX Runtime do fonte com `-Wl,-z,max-page-size=16384`) **não é necessário**. Relatório: `docs/spikes-android/AT0.md`. Falta só a confirmação de runtime (`zipalign`, emulador 16 KB), que depende de `app/android/` existir e entra no aceite normal. |
| 2026-07-13 | **Achado — a sincronia do pipeline não é 100% reprodutível, e o `tool/integration_test.dart` escondia isso.** O teste regerava a fixture com o Piper a cada execução; o Piper é um VITS com `noise_scale_w=0.8`, ou seja, síntese **estocástica** → áudio de entrada diferente a cada run → timestamps e segmentação diferentes (medido: 4–6 unidades para o mesmo texto; sincronia 83%–100%). Corrigido: a fixture agora é gerada uma vez e reusada (apagar o jobDir força uma nova). **Porém**, mesmo com fixture de SHA-256 idêntico, a segmentação ainda oscila 5↔6 unidades: whisper-cli e o spleeter são individualmente determinísticos (transcript/vocals com hash idêntico em 3 execuções), mas a inferência nativa multi-thread sob carga introduz jitter sub-ms nos timestamps que ocasionalmente cruza o limiar de merge (`mergeMaxPause = 600ms`), criando/removendo uma unidade. É uma fragilidade pré-existente (não do refactor do DubbingRuntime) e relevante para o baseline de ±300ms da fase D1: o baseline precisa ser uma faixa/mediana de N execuções, não um número único. |
| 2026-07-12 | **Bug corrigido — o fallback de re-encode do mux nunca funcionou.** `muxer.dart` pedia `-c:v libx264`, mas o ffmpeg distribuído em `tools/win/` é build LGPL com `--disable-libx264` (conferido no `-buildconf`): o encoder **não existe no binário**. Ou seja, o caminho que existe justamente para salvar containers cujo codec o MP4 não aceita (VP9 de um WebM) falhava sempre, com "Unknown encoder 'libx264'". Trocado por **`libopenh264`** (`--enable-libopenh264`, LGPL, já presente), com `reencodeVideoBitrate = '5M'` — o openh264 não aceita `-crf`/`-preset`. O mesmo `libx264` estava no `tool/integration_test.dart` e impedia a geração da fixture. **Por que passou despercebido:** os dois testes de muxer *asseriam* `args.contains('libx264')` com o ffmpeg **mockado** — validavam a string, nunca executavam o comando. Agora asserem `libopenh264` e a **ausência** de `libx264`. |
| 2026-07-12 | **Sincronia vira métrica do próprio pipeline.** O critério "≥90% dos segmentos em ±300 ms" era verificado à mão (amostragem no VLC) e só na fase final. O pipeline passa a gravar `sync_report.json` por job (`origStart`, `placedStart`, `delta`, `speedUsed`, `atempoUsed`, `overflow`, `truncatedMs`), medido no Windows já na fase D1 como baseline e reusado sem trabalho extra no Android. Motivo: o `OfflineRecognizer` do sherpa **não devolve timestamps para Whisper**, enquanto o desktop hoje roda `whisper-cli -ml 1 -sow` (um segmento por palavra) — a granularidade temporal muda no port, e isso precisa ser medido, não presumido. |
| 2026-07-14 | **Achado — `adb push`/`adb shell mkdir` para dentro de `Android/data/<pkg>/files` cria arquivos invisíveis ao próprio app.** Descoberto ao rodar o AT-2 no device: qualquer diretório/arquivo criado via shell (uid `shell`) dentro da pasta externa de um app dá `Permission denied` quando o **próprio app** (uid próprio) tenta `existsSync`/`createSync` no mesmo caminho — mesmo sendo a pasta do próprio app. Só sobrevive o que o processo do app cria diretamente. Contorno usado no spike: enviar os assets para `/data/local/tmp` (sem isolamento por app) e o app copiar para sua própria pasta no primeiro start. **Não afeta produção** — lá o `ModelManager` sempre baixa/escreve pelo processo do app, nunca via adb. Relevante só para quem for montar fixtures/benchmarks manuais no device. |
| 2026-07-14 | **Achado de ambiente — build Gradle/Flutter no Windows pode esgotar memória VIRTUAL (commit charge), não RAM física.** Ao compilar o app de benchmark do AT-2, `flutter build apk` crashava o daemon Gradle/JVM com OOM repetidamente mesmo com RAM física livre — `Get-CimInstance Win32_OperatingSystem` mostrava `FreeVirtualMemory` baixo (pagefiles fixos, não auto-gerenciados nesta máquina: `C:\pagefile.sys`=4073 MB, `E:\pagefile.sys`=8192 MB). É um teto de commit charge do SO, distinto de falta de RAM. **Mitigação que funcionou** (`android/gradle.properties`): `org.gradle.jvmargs=-Xmx512m -XX:+UseSerialGC -Xss512k` (G1GC reserva muito mais espaço virtual de saída que o Serial), `org.gradle.daemon=false`, `org.gradle.workers.max=1`, `kotlin.compiler.execution.strategy=in-process` (evita um segundo JVM só para o compilador Kotlin). **Armadilha decorrente:** se um build travado for cancelado, o processo Java filho pode sobreviver ao encerramento do processo pai (shell) e ficar segurando o lock `<GRADLE_USER_HOME>/caches/journal-1/journal-1.lock` — o próximo build falha em segundos com "Timeout waiting to lock journal cache", parecendo um novo erro quando é só um daemon zumbi. Sob essa pressão de memória, `tasklist`/`taskkill` (utilitários clássicos do Windows) também podem travar/dar timeout; `Stop-Process -Id <pid> -Force` do PowerShell (via API .NET) contorna. |
| 2026-07-14 | **Achado de ambiente — `adb push`/`adb shell` via Git Bash (MSYS) corrompe paths que começam com `/`.** O runtime MSYS2 do Git Bash reescreve automaticamente argumentos que parecem paths POSIX absolutos (`/storage/emulated/0/...`) para paths Windows (`E:/Git/storage/emulated/0/...`) antes de repassar a um `.exe` nativo como o `adb`. O sintoma é sutil: o comando roda sem erro fatal e até imprime "N file pushed", mas os arquivos vão para o destino errado — só aparece ao verificar com `adb shell find` depois. **Fix:** `export MSYS_NO_PATHCONV=1` antes de qualquer bloco de comandos `adb push`/`adb shell` com paths absolutos do device. |
| 2026-07-14 | **AT-2 executado no moto g86: PASSOU.** RTF 0,138–0,267 (teto: <1), pico de app 711 MB (teto: 1,5 GB), zero regressão de timestamp, zero janela perdida nos 6 combos (en/pt/es × tiny/base).
